# PR 1.5 — Invoke a real skill after single-engine recovery

## Outcome

An authorized caller receives the known output of a real skill through Go after its publication is restored on a replacement JVM. This proves the complete single-engine milestone through the actual invocation path.

## Requirements

- Implement the synchronous JSON invocation path needed for the milestone. Go authorizes the caller for the application and routes only to an eligible observed placement. The shared Go invocation logic applies the agreed limits before dispatch, including the inclusive 20 MiB limit on the complete JSON request body. The shared limits also specify up to 25 uploaded files for multipart invocation when that transport is added. REST, MCP, and UI entry points use the same Go logic as they are wired.
- Send `namespace`, exact local skill name as `skill`, the `input` object, and the authenticated `caller` object separately over mTLS to Java at `POST /internal/v1/invoke`. Java requires nonblank issuer and subject and an array of application roles, allowing an empty array. Establish the Framework principal from issuer and subject, apply the `ROLE_` prefix once, and let Framework select the generation and enforce skill permissions. For a direct user, Go supplies the Cloud issuer, signed-in subject and roles assigned for this application. Accept a backend’s end-user ID and roles only from a backend authorized for this application, using that authenticated backend as issuer. Pass namespace and local name separately to `SkillTemplate.invoke`.
- Framework selects the generation when it accepts the invocation. Already-accepted work, including reachable child skills, finishes on its captured generation. A request in transit across activation uses the replacement if Framework accepts it after activation. Apply this rule for every input shape and transport. Go and Java must leave generation selection to Framework.
- Return the exact Framework string as JSON `result` on success. Preserve a result containing JSON as a string. Java returns exceptions as non-success JSON with the original `message`, full standard exception output in `debug` (class, stack, causes and suppressed exceptions), and complete `diagnosis` and top-level input-validation `issues` when available. Go exposes the original message and available top-level input-validation issues to an authorized invoker and omits the administrator-controlled diagnostic fields when the switch is off. While no engine is eligible, report temporary unavailability before dispatch. If a dispatched result is unconfirmed, report unknown outcome without automatic retry. Reserve Java `503` for confirmed rejection before the skill starts. Once execution starts, even a downstream service’s `503` must be represented by a different non-success invoke status. Go treats an authenticated engine `503` as safe to retry. This includes a request in transit when Java closes admission. An intermediary `503` after dispatch leaves the outcome unknown. Caller timeout or disconnect ends the wait while admitted work continues under its Framework deadline.
- Read the application's administrator-controlled switch for each call. It defaults off. Ignore caller attempts to override it. Off means Go omits the wire field, Java invokes without an observer, and Go omits `executionView`, `debug`, and `diagnosis` from caller responses. On means Go sends `executionView: "always"`, Java captures the observer’s complete view (session ID and events), and Go returns it on success and skill failure, plus available `debug` and `diagnosis` on failure. When requested but unavailable, return `"executionView": null` and preserve the status, result or error details. Trace retention is independent.
- Verify the cumulative milestone with one engine pod at a time. Start with no Cloud applications, publish a reference-free pack (`loomspan: {}`, empty `variableValues`, complete Cloud runtime settings) through Go on its first request immediately after the first authenticated snapshot, and confirm the requested version on that JVM. Verify that a failed replacement leaves that version serving. Publish a newer version and terminate the pod after Go durably records Java’s `204` and before Console observes the new version. Verify that Go restores that version on the replacement and first invokes the restored publication only after Console confirms the namespace and version on the new JVM.
- Use the private namespace `milestone`, local skill `echo-release`, and input `{"text":"ping"}`. In the milestone test deployment, register a deterministic executor in a host namespace accessible to the private skill. Keep the `milestone` application absent at startup. Both ZIPs publish `loomspan/skills/echo-release.yaml` with a qualified reference to that executor and a required string input named `text`. Its skill `config` supplies a literal release label and it returns that label, a slash, and the input text. The original pack gives `first/ping`, the newer pack gives `restored/ping`. Use the same test host on both JVMs, with the label coming exclusively from the installed pack. For the skill-error checks, the same executor throws on `{"text":"fail"}` after invocation starts. This exercises a real skill failure independently of the pre-session rejection used for the null-view check.

## Acceptance criteria

- [ ] The authorized JSON call forwards the correct identity and roles, runs through Java and Framework, and returns the exact expected result through Go. Invalid caller metadata or unauthorized access does not run the skill. A valid body of 20,971,520 bytes can be dispatched. One byte more is rejected in Go before dispatch.
- [ ] With trace persistence `NEVER`, exercise all four combinations of switch off/on and a successful return/real skill error. Assert the internal request mode, caller-visible field presence and contents, and original result or message and available issues in each case. With the switch on, verify the null-view fallback when rejection precedes session creation or finalization cannot deliver a view.
- [ ] No eligible engine causes a pre-dispatch temporary-unavailable response. An intermediary `503` or lost response after dispatch yields unknown outcome with no automatic retry. An authenticated engine `503` confirms pre-execution rejection. An already-started skill failing because its provider was unavailable cannot produce that signal.
- [ ] In the cumulative K3s recovery scenario, verify the first publish succeeds and its `204` triggers a refresh confirming the original version on the first JVM before any invocation. Reject an invalid replacement and confirm the previous version still serves. Use a separate invocation check for `first/ping` so the first caller invocation in the recovery scenario exercises the restored publication. Capture the later `204` and durable pointer, withhold observation of the newer version on the old JVM, then replace the pod. Observe zero invoke dispatches until Console confirms the requested namespace and version on the new, eligible JVM. The first invocation must then return a JSON object with only `result`, whose exact string value is `restored/ping`, through Go with the switch off. Record the old and replacement JVM IDs and the restored publication version.
- [ ] Across successful replacement on a live JVM, observe an already-admitted call finishing on its original generation and a newly accepted call using the replacement. Hold one JSON request in transit until activation, then let Framework accept it and verify it uses the new generation. For the already-admitted call, check a reachable child still uses its captured generation.
- [ ] Verify the executable Spring Boot JAR with `mvn verify` in `execution-engine/` using JDK 21, Maven 3.9+, and the Framework starter snapshot. The cumulative Go build and focused K3s milestone checks pass.

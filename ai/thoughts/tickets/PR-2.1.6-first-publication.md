# PR 2.1.6 — Publish the selected staged revision and durably confirm its installation

## Outcome

A Manager explicitly publishes the chosen current staged revision. The REST caller receives a stable request ID for every accepted Publish, including a failed attempt. On success, Go also returns the confirmed version after recording installation in the application’s private namespace.

## Context

GitHub PR 2, Go backend Phase 1. Depends on PR 2.1.3–2.1.5 for authenticated observation and Java calls, application authorization, staging, immutable ZIP references, validation and effective settings. This ticket covers initial publication and overlapping Publishes for one application within the lifetime of a Go process. Phase 2 extends that behavior to application restarts and recovery across process or engine replacement.

## Requirements

Apply PR 2.1.3’s [dispatch eligibility for Validate and Publish](../future/go-backend-roadmap.md#dispatch-eligibility-for-validate-and-publish) before each new Validate or Install call. Exercise an otherwise publishable selection while both pod UIDs are visible throughout the request. Return the accepted request ID and recorded placement failure with zero Java calls. For an already-dispatched Install, use the original pod UID and JVM instance ID for snapshot confirmation.

Implement this ticket’s public routes, request bodies, response fields and statuses from the [Phase 1 Cloud REST API](../future/phase-1-rest-api.md).

- After checking Manager access, compare the caller’s selected revision ID with the application’s current staged revision ID. A mismatch ends the Phase 1 request with a warning naming both IDs, even if the selected revision is already published. Only a match proceeds to the current-publication check: if that revision is already published, return “This revision is already published.” Both early returns precede acceptance, fresh validation and Java dispatch.
- Phase 1 takes only the selected revision ID for this decision. Leave the confirmation parameter and confirmed publication of a noncurrent revision to Phase 2. The comparison uses the current staged revision read by Go; it requires no caller-supplied staging ETag or precondition token.
- For a new installation, lock the application row with `SELECT ... FOR UPDATE`, verify the ZIP exists, and commit the request ID, operation, actor, target version and protected ZIP reference. A missing ZIP requires re-upload and leaves the request unaccepted. Commit before checking engine eligibility, checking required variable values, or running fresh validation, even if Go already knows the engine is down.
- If an accepted attempt fails before install dispatch, persist the terminal failure and specific reason on its request row and return its ID and diagnostic. This includes an invalid pack, missing or blank variable, incomplete validation, missing current snapshot, or observed shutdown. Preserve acceptance order for Phase 2’s latest-operation lookup. Release this request’s ZIP protection, preserve staging and the current publication, and exclude the failed target from confirmed pack history.
- Expose a REST GET scoped by application ID and request ID. Check current Manager access to the named application on every GET, then read the Postgres request row by both IDs. Return the request ID, operation, target version, recorded progress or outcome, failure reason when present, and confirmation time when known. An authorized Manager receives the same 404 for an unknown ID and an ID belonging to another application. The GET reads durable state without contacting Java, refreshing a snapshot, or triggering an install.
- Run fresh validation and fix the revision, required values and complete effective settings in memory for this attempt. Missing or blank references block installation with source/path feedback. The reference-free first pack uses an explicit empty variableValues map. POST /internal/v1/publish over mTLS with multipart pack and metadata carrying namespace, runtimeSettings and a Cloud-assigned opaque publicationVersion. Require a current authenticated snapshot from the intended engine, and stop new installs to a terminating pod.
- Java’s 204 confirms installation. Request a fresh observation for routing. On a lost install reply, immediately refresh the intended engine’s authenticated snapshot. A matching namespace and target version confirm the installation. After 30 seconds without confirmation, return the original request ID and explain that installation may still complete. The running Go process continues checking fresh observations after the caller’s wait ends. Never resend the original install.
- On confirmation by either path, always record success and the confirmation time on the confirmed request’s own row. In that same Postgres transaction, advance the application’s current-publication pointer only if Go has accepted no newer Publish or Restart for that application. A newer acceptance counts even if that request already failed. On installation failure, preserve the current pointer and pass through a known engine diagnostic.
- If Go accepts Publish B for the same application while Publish A is unconfirmed, persist B with its own request ID. Hold B’s install dispatch until A is confirmed or 60 seconds have elapsed from the start of A’s confirmation wait, whichever comes first. Releasing B at the deadline leaves A unconfirmed. If A later confirms, record success on A’s row and apply the current-pointer transaction rule even if B is still awaiting dispatch.

## Acceptance criteria

- [ ] Hold an accepted Publish behind multiple predecessors. Measure 90 seconds from its first entry into the queue, including advancement past a predecessor. If still queued at expiry, return 202 with `status: "pending"`, its original request ID, operation and target version. Verify zero installs for that request so far and GET it as pending. Release the hold and verify it proceeds in order, dispatches once and the same GET shows the outcome.
- [ ] Make B eligible before its 90-second queue deadline and again exactly at the deadline. In each case dispatch B immediately and return the ordinary outcome on its original POST. Exercise a successful response after more than 90 seconds total through PR 2.1.2’s ingress and Go server. For a lost reply after B’s dispatch, verify its own confirmation window can expire with 202 and `status: "unconfirmed"`.

- [ ] Give fresh Validate and Install separate calls using PR 2.1.5’s shared 30-second deadline. On a Validate timeout, return 503 with the accepted request ID, record the validation-unavailable failure and make zero install calls. After a successful slow Validate, accept an Install 204 whose headers arrive 25 seconds into the Install call.
- [ ] If a connection failure establishes that Install was never sent, record failure on the accepted request. If Java received Install and the connection drops at second 4, start confirmation at second 4. Repeat with Java silent through second 30 and start confirmation at second 30. In each case request an immediate snapshot refresh. While confirmation remains outstanding, measure the 30-second caller wait and 60-second dispatch hold from that start, including time spent awaiting the refresh. Verify a single install dispatch for the request.

- [ ] Seed a `Deleting` application and call Publish as Manager. Return `409 Conflict` with reason `Deleting` before comparing revisions or accepting a request. Exercise a stale selection, an already-published selection and an otherwise publishable selection. Each leaves staging and the current pointer unchanged, allocates no request ID or target version, and makes zero Java calls.

- [ ] Publish A while A is current in staging, then select A again: the second call returns the already-published no-op. Stage B and select A again: this time the response warns that A was selected and B is current in staging. Repeating that selection while B remains staged returns the same warning. Verify both early-return paths leave publication and staging unchanged, allocate no request ID or target version, and make zero Java calls.
- [ ] Publish the current validated pack to the real engine and verify stable request ID, durable confirmed version, exact ZIP reference and a matching fresh namespace observation. Verify repeating Publish for the confirmed revision is a no-op.
- [ ] With A still staged and durably current, supply a fresh replacement-JVM snapshot missing A’s application namespace. Selecting A again still returns “This revision is already published.” Verify zero Java calls, no request ID or target version, and the same current-publication pointer. The missing namespace affects routing eligibility. Phase 2 handles restoration.
- [ ] Start Publish with the engine already disconnected, and separately with the pod already marked terminating. Each eligible selection yields an accepted request ID and a recorded failed Publish stating the corresponding reason. Verify the same ID and reason in the response and durable request record, zero install calls, and an unchanged current publication.
- [ ] Exercise invalid, missing-variable and unavailable-validation cases after acceptance. Each leaves a terminal diagnostic on its own request and releases its outstanding ZIP protection. A stale-selection warning, already-published no-op, denied access, or ZIP removed before acceptance creates no accepted request or target version.
- [ ] Lose A’s reply and let its 30-second caller wait expire. With no newer acceptance, deliver a fresh matching snapshot and verify the same request becomes successful and current without a second install. Verify the success transaction commits before any success is reported.
- [ ] Lose A’s install reply. After the 30-second timeout, GET the request using the returned ID and verify A is unconfirmed. Accept B for the same application, then deliver a matching snapshot for A. Repeat the same GET and verify A’s target version, success and confirmation time even though B is now latest. Verify the GETs make zero engine calls and A is installed only once.
- [ ] GET a failed Publish and verify its recorded reason. As a Manager, compare an unknown request ID with a real request ID from a different application under the same application URL. Both return the same 404. Verify an authenticated nonmember cannot read the request even with the correct pair of IDs.
- [ ] Starting from current publication P, accept B while A is unconfirmed. Exercise both release conditions. If A confirms at 45 seconds, record A’s success, keep P current because B was accepted, and release B immediately. If A stays unconfirmed, verify B can dispatch at 60 seconds measured from A’s original wait. In that case confirm B, then deliver late confirmation for A: both request rows show success, B stays current, and A was dispatched only once.
- [ ] Start with P durably current. Lose A’s install reply, accept B for the same application, and let the hold expire. Have Java reject B’s install and verify B’s request records the failure. Then deliver a fresh authenticated snapshot showing A active. Verify A’s request records success and its confirmation time, B remains the latest accepted request with its failure, and the durable pointer still names P for recovery. The engine may serve A in this state. Processing that snapshot issues no corrective install.

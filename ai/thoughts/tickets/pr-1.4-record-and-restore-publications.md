# PR 1.4 — Record acknowledged publications and restore them from Go

## Outcome

Go can publish a staged pack to an authenticated engine, durably record the acknowledgment, and recover that version on a replacement engine even if Console never saw it on the original JVM. Callers receive staged validation feedback after a completed check and can retry an incomplete attempt.

## Requirements

- Use the selected staged revision and authorized destination application for the shared Go validation and publication operations. Validation sends the authored ZIP and complete effective runtime settings without a value map. Run the engine check even if Cloud finds missing or blank variables. Return diagnostics and Cloud findings together after completion. On an incomplete attempt, tell the caller validation is unavailable and to retry, without partial findings. Keep the result tied to the requested revision and settings even if staging or settings change during validation. An otherwise valid pack passes validation with its missing variables listed as publication blockers. The owner may supply them and publish the same revision directly.
- On publish, compare the named revision with current staging. If they differ, identify both and wait for explicit confirmation to install the reviewed revision. Keep newer staging intact. For a revision already current in publication, report “This revision is already published.” Create no version and send no install. Restart is the operation that reapplies saved edits to that version.
- Before an install, check the selected ZIP’s variable references against the application’s current saved values. Report missing or blank references by pack-relative source and authored YAML path. Send the original ZIP, namespace, assigned opaque publication version, exact value map, and complete effective runtime settings using the engine contract. For each new publication or recovery, compute settings from Cloud policy and the destination’s then-current saved selections. Preserve the settings sent separately from subsequent edits. A fresh Console observation gives the active trace policy.
- For variable discovery, scan the immediate values under `loomspan.connections` and `loomspan.executor-config`, and top-level mapping `config` in executor-backed skills. Traverse keys, values and sequences within those sections. A single-key `$var` mapping names a case-sensitive, nonblank, unpadded YAML string. A multi-key mapping is ordinary data and may contain nested markers. Use Framework’s [conformance cases](../future/application-variable-conformance.md) to compare distinct names and authored occurrence paths, including aliases, excluded fields, and malformed markers. In the effective-key collision case, discovery succeeds. Java’s publish preparation rejects the collision when substituting values. Go sends the original YAML in both phases.
- Allow publish once the first authenticated instance snapshot arrives, even with no installed namespaces. Once Go observes pod termination, withhold both validate and publish, explain shutdown and invite retry when available. Handle responses to requests already dispatched normally. Interrupted validation yields an unavailable result. A lost response after publish dispatch is unconfirmed. Keep that case distinct from an installation Go knows it never sent and from a Java rejection. The [unconfirmed publication procedure](../future/go-backend-roadmap.md#unconfirmed-publications) owns confirmation and explicit retry beyond this ticket. If the current connection lacks a snapshot or Go has observed termination, report that the installation was not sent and can be retried. Surface a received Java publication failure message verbatim to the authorized caller and preserve the current publication.
- Serialize publication dispatch per application, coordinating recovery and owner publication so an older restore cannot overwrite a newer acknowledged install. Keep the immutable ZIP on durable mounted storage. Maintain the publication’s version, ZIP reference, status, and current-publication pointer in Supabase Postgres. After an authenticated `204`, durably record the acknowledged version as current before reporting success. Request an immediate Console snapshot refresh.
- On backend startup, Console reconnection, or discovery of a replacement JVM, compare intended placement with the fresh engine observation. Restore a missing or out-of-date namespace from its current publication using the saved ZIP and version and the application’s current values and effective settings at restore time. Preserve an already-matching installation. Expose routing eligibility only when the intended namespace and publication version are confirmed on a connected, ready, non-terminating pod. A matching generation keeps its already-loaded settings and values. Leave additional, unintended namespaces installed and exclude them from routing. Report each failed restore and continue reconciling the others.

## Acceptance criteria

- [ ] A completed validation of an invalid staged pack reports its findings. Missing variable values are reported with their authored paths in a completed validation, and they do not prevent the engine check. An incomplete attempt invites a retry and returns no partial findings. Changing staging during validation keeps the result with its original revision. Supplying a missing value permits direct publication. Verify the worked corpus yields six occurrences, four distinct lookups, and the skill-only reference.
- [ ] A stale reviewed revision requires explicit confirmation and leaves newer staging intact. Publishing an already-current revision sends nothing and creates no version.
- [ ] Go publishes on the first authenticated snapshot. An install with missing or blank values is blocked before dispatch. Go withholds publish when the current connection lacks a snapshot. Once termination is observed, neither validation nor publication is dispatched, and the caller learns why and when to retry. A received Java failure reaches the caller with its original message and leaves the current publication in place.
- [ ] On `204`, the durable record points to the original saved ZIP and the acknowledged version by the time the caller sees success. Exercise recovery overlapping a newer publish for the same application. With both responses acknowledged, the engine and durable pointer end on the newer publication. A successful install requests a snapshot refresh. Routing eligibility stays closed for the requested version until Console confirms it on the eligible JVM.
- [ ] A lost pod after the durable acknowledgment and before observation of the new version causes Go to restore that version, even if Go must reload the record. Recovery uses the original ZIP and current saved inputs. A fresh matching observation allows reuse without reinstalling, even if saved variables changed while the backend was offline. A failed restore is reported per application while other restores continue and already-confirmed namespaces serve. An extra observed namespace remains loaded and ineligible. Verify a settings edit during installation stays distinguishable from the confirmed active policy.
